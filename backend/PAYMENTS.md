# 交易、支付与人工结算

本文件记录本次讨论确认的业务规则及代码边界。旧 P0–P4 文档保留为设计来源，不作为本模块的现行规则。

## 已确认的业务规则

- 跑腿、辅导、咨询等普通服务先履约后付款。服务方提交完成，需求方手动验收或提交完成后24小时无异议自动验收。
- 验收后有1小时正常付款期；超时提醒、标记并一次性扣10分，再经过24小时未付款则转管理员。无确认且无异议的完整时间线为提交完成后24小时验收、25小时扣分、49小时管理员介入。
- 需求验收方提出“服务未完成”或“质量不符”的正式异议后，暂停自动验收、扣分和升级计时；管理员裁决付款义务与期限。服务方的催款投诉不会反向暂停追缴。
- 使用真实微信Native、支付宝当面付收款。后台验签通知或查单确认支付，前端跳转、二维码生成和请求超时均不能确认已付款。
- 普通商户暂未开通自动结算。本版由管理员先实际向服务方转账，再登记转账流水、等额金额和凭证。数据库状态为`recorded`，表示登记人工结算，不表示渠道已执行自动打款。
- 本版不额外收取平台佣金，不擅自从约定报酬扣渠道手续费；人工结算登记金额为约定全额，渠道手续费由平台承担。新增收费规则须另行确认并更新报价与测试。
- 封禁后保留受限登录，只允许本人订单、付款、投诉和账号安全操作，不能发布、接单或使用其他普通业务入口。每次请求从数据库重载权限，封禁无需等待旧JWT自然过期。
- 组队仅无偿招募，数据库金额为空、订单金额为0，前端不展示金额。沿用人数上限包含发起人的定义，未满员时允许多名参与者加入。
- 辅导总价按发布时约定的时薪乘时长计算，人民币分四舍五入；接单时冻结总金额。二手出售由买家付款给卖家，不能按照“发布者必定付款”推断方向。
- 需求验收方单向评价服务提供方。有偿订单支付成功后开放评价，无偿订单验收后开放；七天未评默认四星，不因此加分。
- 初始信用100分，限制在0–100分；五星加1，一二星减1，三四星不变；发布和接单至少70分。沿用低于70分每日恢复1分、到70分停止的规则，以日期唯一记录防止重启或多实例重复恢复。
- 真实逾期后补付不会自动返还已扣分。若渠道证明付款实际发生在期限内，只是回调晚到，则按原实际扣分额撤销误罚。额外处罚由管理员给出理由，不按金额自动猜处罚档位。

## 实现与审查入口

| 内容 | 入口 |
|---|---|
| 提交、验收、争议与付款期限 | `OrderLifecycleService` |
| 接单行锁、金额与双方快照 | `OrderService` |
| 官方SDK、微信验签解密、支付宝RSA2 | `WechatPaymentGateway`、`AlipayPaymentGateway` |
| 支付预留、金额/商户核对、幂等记账 | `PaymentTransactionService` |
| 网络调用及查单补偿 | `PaymentService` |
| 人工结算和私有凭证 | `SettlementService`、`SettlementEvidenceStorage` |
| 单向评价、七天默认四星 | `ReviewService`、`AutoReviewScheduler` |
| 信用审计与每日恢复去重 | `CreditService`、`CreditScoreScheduler` |

业务时间统一为`Asia/Shanghai`。核心代码注释解释状态迁移、锁顺序、事务与金额来源；测试通过固定Clock验证边界，不使用sleep等待业务时间。

## 商户配置与启用

1. 微信普通商户确认已签约Native支付；支付宝普通商户确认已签约当面付。已有普通商户号不等于已开通所有支付产品。
2. 根据`.env.example`在部署环境或IDE设置变量；Spring Boot不会自动读取该示例文件。
   认证模块另需至少64字节的JWT密钥、32字节AES密钥及可用校邮SMTP配置。验证码不再回显；注册验证码绑定申请时的学号，未注册账号先注册再使用验证码登录。现有校邮验证不冒充手机归属验证或学校SSO。
3. 商户私钥、微信支付公钥、支付宝公钥放在仓库外，通过文件路径配置。当前支付宝适配器使用RSA2公钥模式，不能把证书模式文件当成公钥字符串直接使用。
4. 配置公网HTTPS回调：`/api/v1/payments/notify/wechat`和`/api/v1/payments/notify/alipay`。代理须保留微信原始请求体及签名头；支付宝表单参数不能被重复拼接或重新编码。
5. 开启对应`CAMPUSHUB_*_ENABLED`。缺少必要商户参数时启动失败；默认关闭，不返回模拟支付二维码。
6. 在渠道支持的测试环境验证收款、通知、重复通知和查询补偿；生产小额联调需运营方明确指定金额、付款人、收款人及退款处理，CI不自动执行真实资金交易。
7. 确保人工结算由可靠管理员执行，私有凭证目录已持久化和备份。前端管理员入口为`/admin/finance`。

每个业务订单最多一张有效支付单，失败重试沿用原单；本版不允许仍可支付的原单跨渠道重新开单。旧单经渠道确认关闭后才可重开，全部历史记录保留。不能把仍可支付的二维码金额直接改写为另一个金额，以免旧码仍收取原金额。

## 当前资金边界

收款成功与服务方收到转账分别记录，平台不会用普通商户收款结果冒充给服务方的自动结算。自动分账及自动打款未启用，也没有用未开通的产品返回假成功。

管理员可对尚未签发支付单的未付款争议裁定应付金额与期限。已签发渠道单或已经付款后，如裁决涉及改价或退款，须先由运营方在商户渠道完成关单/退款核对；现有接口会拒绝直接覆盖金额，保留争议和付款证据。本版未宣称接入尚未讨论的自动退款政策。

旧订单没有可靠支付记录，不自动推断已付或未付，也不补扣历史逾期分数。`amountDue=NULL`的历史订单必须人工核对；新交易规则仅作用于接单时生成了金额快照的订单。

## 数据库升级

升级前备份数据库、旧收款码资料及私有凭证。先在数据库副本执行`SQL/04-payment-migration.sql`，核对迁移结果，再发布应用。

迁移不删除旧支付码字段，不把历史订单自动变成新欠款。原来误映射到`second_hand_task`的二手数据会复制到正式`t_task_flea`表，并保留原表供核对。

GitHub的MySQL任务会另外建立`campushub_migration_ci`，装入旧结构夹具、执行两次迁移，并检查历史订单未变欠款、原凭证保留及二手数据复制。本地没有MySQL时不能将H2通过当成这一步已经运行。

开发默认保留`ddl-auto:update`；生产应在完成迁移核验后设置`SPRING_JPA_HIBERNATE_DDL_AUTO=validate`。不要把应用自动建表当作生产数据迁移和验收。

## 验证范围

运行`mvn -B -ntp clean verify`，检查Surefire报告及`target/site/jacoco/index.html`。订单、支付、评价三个包分别要求至少60%行覆盖率；不以全项目覆盖率或成功用例数冒充资金流程验证。

集成测试保留真实过滤器、Service、事务与数据库，仅替换外部渠道网络。独立验签测试使用运行时生成的RSA密钥、真实官方SDK和微信AES-GCM通知。测试通过不等于已完成真实商户签约、生产回调或真实到账验收。

官方接入依据：[微信Java SDK](https://github.com/wechatpay-apiv3/wechatpay-java)、[支付宝Java SDK](https://github.com/alipay/alipay-sdk-java-all/tree/master/v2)、[微信回调与查单指引](https://pay.wechatpay.cn/doc/v3/merchant/4012075249)。
