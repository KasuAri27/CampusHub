# 3个详细用例描述

## 1. 用例1：需求方发布需求

| 字段 | 内容描述 |
| --- | --- |
| 角色 | 需求方 |
| 前置条件 | 1. 用户成功注册账号，登录完成<br>2. 信用分>=60 |
| 基本流 | 1. 学生进入平台，点击“发布需求”<br>2. 学生选择需求类型，如快递代取，二手交易，问题咨询，组队匹配等<br>3. 系统给出学生需填写的信息<br>4. 学生填写任务标题，具体描述，时间地点，报酬<br>5. 学生点击“确认发布”<br>6. 系统审核之后，需求成功发布，首页需求列表更新<br>7. 学生收到“需求发布成功”的提示 |
| 替代流 | 1. 用户未完成登录，系统提示“先完成账号登录”<br>2. 用户信用分<60，系统提示“信用分过低，无法发布需求”，可引导学生联系管理员<br>3. 学生填写信息不完整，系统提示“请完善信息”<br>4. 系统审核不通过，向学生提示具体违规内容<br>5. 学生取消发布，系统退出信息填写页面，不保存任何数据 |
| 后置条件 | 1. 需求发布成功，状态显示为“待接单“<br>2. 系统推送需求给服务方 |

## 2. 用例2：服务方接收订单

| 字段 | 内容描述 |
| --- | --- |
| 角色 | 服务方 |
| 前置条件 | 1. 学生已注册账户，且登录完成<br>2. 信用分>=60<br>3. 目标需求状态为“待接单“ |
| 基本流 | 1. 服务方在平台首页浏览需求列表<br>2. 服务方点击任务查看详情<br>3. 服务方确定接单，点击“接单“，系统提示”是否确认接单“<br>4. 服务方确认，系统校验接单资格<br>5. 订单状态更新为“进行中“<br>6. 系统向发布者发送“已有人接单“的通知 |
| 替代流 | 1. 订单已被他人接单，系统提示“该需求已被接单“，刷新订单状态<br>2. 需求已过期，系统提示“该需求已过期，无法接单“，刷新订单状态<br>3. 服务方信用分<60,系统提示“信用分过低，不予接单“，引导服务方咨询管理员<br>4. 发布者取消订单，系统提示“该需求已被取消，无法接单“ |
| 后置条件 | 1. 订单状态改为“进行中“，其他用户无法接单<br>2. 服务方被认定为订单的承接方 |

## 3. 用例3：管理员处理举报信息

| 字段 | 内容描述 |
| --- | --- |
| 角色 | 管理员 |
| 前置条件 | 1. 管理员进入后台系统<br>2. 管理员具有举报处理权限<br>3. 存在“待处理“的举报信息 |
| 基本流 | 1. 系统确认该用户的管理员身份，管理员登录后台系统<br>2. 管理员点击“举报模块“<br>3. 管理员点开举报记录，查看详细信息<br>4. 管理员确认举报人，被举报人，举报理由，证据提供<br>5. 管理员判断举报是否成立，选择结果：<br>成立/不成立，填写处理结果备注（可选）<br>6. 管理员提交处理结果<br>7. 系统更新举报信息状态为“已处理“，并向双方发布处理结果通知 |
| 替代流 | 1. 举报信息被撤销，向管理员提示“举报信息已撤销，无需处理“<br>2. 证据不充足时，管理员选择“待补充证据“，系统向举报方发送补充证据的通知，举报信息状态更新为”待补充证据“<br>3. 管理员误判，可由举报者申诉，管理员再次处理 |
| 后置条件 | 1. 举报信息状态更新为“已处理“<br>2. 处理结果发送至涉及的双方<br>3. 举报成立，系统对被举报方进行扣分或封禁 |
