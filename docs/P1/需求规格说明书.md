# 需求规格说明书

编写：卫苏协议小组       日期：2026-04-15

## 1. 引言

### 1.1 目的

本文档旨在定义校园互助服务平台的功能、性能、用户界面及设计约束，确保开发团队与利益相关者对需求达成共识，为系统设计、开发和测试提供依据。

### 1.2 范围

该平台面向大学生，覆盖学生的互助需求，包括快递代取，二手交易，学习辅导，组队招募，问题咨询等场景，支持身份认证，发布接单，支付及评价等功能。

### 1.3 定义

| 术语 | 解释说明 |
| --- | --- |
| 需求方 | 提出需求并验收付款的学生 |
| 服务方 | 承接需求并提供服务的学生 |
| 管理员 | 管理维护平台、审核需求、处理财务人工结算与投诉纠纷的学生 |
| IEEE 830 | 软件需求规格说明标准 |

## 2. 总体描述

### 2.1 产品视角

大学校园内学生互助需求频繁，但现有解决方案（微信群、QQ群、贴吧）存在信息分散、匹配效率低、信任机制缺失等问题。

本平台旨在整合需求，提供高效、透明、有信用保障与资金担保的互助服务。

### 2.2 用户特征

| 用户 | 特征 |
| --- | --- |
| 需求方 | 有临时需求，对履约时效、服务质量、资金安全性敏感 |
| 服务方 | 利用碎片时间赚取报酬或无偿互助，注重结算及时与评价公正 |
| 管理员 | 审核需求内容，维护平台秩序，执行线下结算核验与争议仲裁 |

### 2.3 约束

• 技术栈：前端：Vue 3 + Vite + Element Plus + Pinia + Vue Router（桌面端 Web SPA）；后端：Java 17 + Spring Boot 3 + Spring Data JPA；工程构建：Maven；数据库：MySQL 8.0；持续集成：GitHub Actions。（注：移动端多端适配与 Redis 缓存中间件作为后续演进，记录于根目录 `TODO.md`）

• 合规性：需符合《网络安全法》《个人信息保护法》，密码与敏感凭据强加密存储。

• 部署环境：校园私有云或第三方云服务，业务时间统一采用 `Asia/Shanghai`。

### 2.4 假设

• 假设校园网络稳定，用户可通过现代浏览器访问 Web 端。

• 依赖第三方支付签约渠道（微信 Native 支付、支付宝当面付）及校邮 SMTP 验证码服务的可用性。

## 3. 功能需求

### 3.1 REQ-001 身份认证

学生使用学号/手机号/校邮完成注册与认证，登录基于 JWT 无状态 Token。仅认证通过且信用分达标（≥70分）者可发布需求或接单。

### 3.2 REQ-002 需求发布

#### 3.2.1 功能描述

用户可填写需求类型、标题、描述、时间、地点、校区、报酬等信息并提交。提交后进入待审核状态（`pending_review`），审核通过后公开显示在广场（`published`）。

#### 3.2.2 输入

• 需求分类（快递代取 / 学习辅导 / 二手交易 / 组队招募 / 问题咨询）

• 标题（文本，≤30 字）

• 描述（详细服务诉求）

• 截止时间（日期时间选择器）

• 校区与地点（校区下拉框：鼓楼、仙林、浦口、苏州；手动输入详细地址。注：地图 SDK 图形化选点作为后续扩展，记录于根目录 `TODO.md`）

• 报酬（数字，辅导支持时薪×时长计算，二手由买家付款给卖家，组队招募无偿且金额为 0）

#### 3.2.3 输出

需求提交成功并进入审核队列。管理员审核通过后需求卡片展示在需求广场，包含标题、报酬、时间、校区、地点等信息。

#### 3.2.4 异常处理

• 用户信用分低于 70 分时禁止发布需求。

• 截止时间已过期或输入不合法时提示错误。

### 3.3 REQ-003 需求检索与匹配

#### 3.3.1 功能描述

用户可根据校区、分类、关键词对广场需求进行多维度筛选与列表浏览。

#### 3.3.2 输入

• 校区筛选（鼓楼 / 仙林 / 浦口 / 苏州）

• 分类筛选（跑腿、辅导、二手、组队、咨询等）

• 关键词搜索（支持标题与描述模糊检索）

（注：基于 GPS 经纬度的距离排序与标签智能推荐作为后续扩展，记录于根目录 `TODO.md`）

#### 3.3.3 输出

符合条件的需求列表分页展示，支持查看需求详细信息。

#### 3.3.4 异常处理

• 无匹配结果时提示“暂无相关需求”。

### 3.4 REQ-004 接单与状态机流转

#### 3.4.1 功能描述

学生可浏览需求详情并接单承接服务。系统通过数据库互斥悲观锁机制保障先到先得抢单唯一性，避免并发超接。

状态机流转规则：
- **需求状态机**：
  `pending_review`（待审核）→ `published`（已发布）→ `in_progress`（进行中/已接单）→ `completed`（已完成）/ `cancelled`（已取消）。
  - 若管理员审核驳回，当前直接置为 `cancelled` 并发送站内信通知驳回原因；
  - 后续计划增加独立 `rejected`（被拒绝）状态并支持修改后重新提交，已记录于根目录 `TODO.md`。
- **订单状态机**：
  服务方接单后生成订单，状态为 `in_progress`（进行中）→ 服务方提交完工后进入 `awaiting_acceptance`（待验收）→ 需求方手动验收或 24 小时自动验收后进入 `completed`（已完成）/ 取消（`cancelled`）。

#### 3.4.2 输入

• 点击“立即接单”按钮（需登录且信用分 ≥ 70 分，且不可承接本人发布的需求）

#### 3.4.3 输出

接单成功生成关联订单，需求与订单状态更新为 `in_progress`，双方开启订单协同并自动创建即时沟通会话。

#### 3.4.4 异常处理

• 需求已被他人承接时提示“该需求已被接单”。

• 用户自身信用分低于 70 分时提示“信用分不足 70 分，暂无法接单”。

### 3.5 REQ-005 单向评价与信用分体系

#### 3.5.1 功能描述

订单完工后（有偿订单支付成功后，无偿订单验收完成后），需求验收方可对服务提供方发起单向评价（服务方不能反向评价需求方）。评价仅对开放评价的业务分类（`category.hasReview == true`）生效。

#### 3.5.2 输入

• 评分：1-5 星整数

• 评价文本：≤200 字纯文本（不支持图片上传）

#### 3.5.3 评价输出与信用分规则

• 评价提交后公开展示在服务方主页及订单历史中，并根据评分实时结算信用分：
  - 5 星好评：服务方信用分 +1；
  - 1-2 星差评：服务方信用分 -1；
  - 3-4 星中评：服务方信用分保持不变；
  - 订单完工满 7 天需求方仍未评价的，系统调度任务自动触发 4 星默认好评（不增减信用分）；
• **信用分基本盘**：
  - 初始分 100 分，取值范围为 [0, 100] 分；
  - 发布需求与接单的最低准入门槛均为 70 分；
  - 低于 70 分的用户，系统在每日零点自动执行补偿恢复任务，每天恢复 1 分，直至达到 70 分停止恢复；底层通过日期唯一记录（`credit_recovery_runs`）保证集群与重启幂等，防止多实例重复加分。

#### 3.5.4 异常处理

• 订单未完工或已评价时禁止重复评价。

• 遇到恶意差评或履约纠纷，参与方可发起申诉投诉，由管理员介入裁决处理。

### 3.6 REQ-006 真实支付与线下人工结算

#### 3.6.1 功能描述

平台采用“先履约后付款、平台真实扫码代收、管理员线下打款并上传凭证记录”的资金安全模型（彻底弃用服务方上传个人收款码和假结算机制）：
1. 服务方完成服务后在系统提交完工（进入 `awaiting_acceptance`）；
2. 需求方手动点击确认验收，或完工提交满 24 小时无异议由系统调度自动验收（进入 `completed`，生成待支付账单）；
3. 需求方在验收后 1 小时正常付款期内，通过微信 Native 或支付宝当面付扫码向平台签约商户号支付报酬；
4. 普通商户暂不具备自动分账权限，报酬结算由管理员在线下向服务方真实打款转账（全额转账，平台不抽取佣金，手续费由平台承担），随后在后台（`/admin/finance`）上传转账凭证文件（PNG/JPG/PDF）登记人工结算流水（`recorded`）。

#### 3.6.2 输入

• 支付渠道选择（微信 Native 二维码 / 支付宝当面付二维码）

• 外部手机 App 扫码付款授权

#### 3.6.3 输出

• 官方异步回调验签解密或后台轮询查单，确认资金到账后订单付款状态更新为 `paid`；

• 管理员线下打款并上传凭证后，订单结算状态更新为 `recorded`，并生成资金流水记录与私有凭证归档。

#### 3.6.4 异常处理与超时违规机制

• **逾期未付提醒与处罚**：验收后超过 1 小时未付款，系统下发催款站内信，标记逾期并一次性扣除需求方 10 分信用分；
• **升级管理员介入**：验收后满 25 小时（逾期 24 小时）仍未付款，订单自动升级流转至管理员财务待办中心介入追缴；
• **服务异议机制**：若需求方在 24 小时验收期内提出“服务未完成”或“质量不符”的正式异议，系统立即暂停自动验收、扣分与升级倒计时，转由管理员裁定最终应付金额与期限。

## 4. 非功能需求

### 4.1 性能需求

• 响应时间：首页加载 ≤ 2 秒，API 检索响应 ≤ 1 秒。

• 并发控制：接单、支付、信用分恢复等核心操作严格通过事务隔离与行级悲观锁保障强一致性。

### 4.2 安全需求

• 数据加密：登录密码采用 BCrypt 强哈希散列，学号与真实姓名等高敏感信息采用 AES-256-GCM 密文持久化。

• 权限控制：Spring Security + JWT 鉴权，封禁用户保留受限登录只读本人数据，接口层实现越权防护。

• 交易安全：微信支付 AES-GCM 验签解密，支付宝 RSA2 验签，凭证私有目录安全存储。

### 4.3 可用性需求

• 界面友好：遵循 Element Plus 交互范式，清晰展示订单状态、倒计时与支付二维码。

• 7×24 小时稳定运行，系统时间基准严格统一为 `Asia/Shanghai`。

### 4.4 可扩展性需求

• 架构解耦，支持后续平滑引入 Redis 缓存与分布式锁。

• 字段设计预留经纬度坐标与地图 SDK 接口。

## 5. 外部接口需求

### 5.1 用户接口

• 采用 Vue 3 + Element Plus 构建的 Web SPA 响应式界面，主流现代 PC 浏览器（Chrome, Edge, Firefox, Safari 等）全面兼容。

• 移动端适配及微信小程序规划详见根目录 `TODO.md`。

### 5.2 硬件与展示接口

• PC 屏幕动态渲染原生支付二维码，学生使用微信/支付宝手机客户端直接扫码付款。

• 原生硬件调用（如手机 GPS 定位、摄像头）规划详见根目录 `TODO.md`。

### 5.3 软件接口

• 微信支付 SDK：官方 `wechatpay-java` Native 扫码支付与回调解密。

• 支付宝 SDK：官方 `alipay-sdk-java-all` 当面付扫码与 RSA2 验签。

• 邮件通知：校邮 SMTP 发送验证码。

### 5.4 通信接口

• HTTP/HTTPS：RESTful JSON 数据交互，标准状态码规范。

## 7. 附录

### 7.1 术语表

• **信用分**：100 分制整数，范围 [0, 100]，初始 100 分。5 星 +1，1-2 星 -1，3-4 星不变，7 天未评默认 4 星（不加分）。发布与接单门槛为 70 分，低于 70 分每日零点补偿恢复 1 分（上限 70 分）。

• **需求状态机**：`pending_review`（待审核）→ `published`（已发布）→ `in_progress`（进行中）→ `completed`（已完成）/ `cancelled`（已取消）。驳回暂置为 `cancelled`，`rejected` 状态规划见 `TODO.md`。

• **订单状态机**：`in_progress`（进行中）→ `awaiting_acceptance`（待验收）→ `completed`（已完成）/ `cancelled`（已取消）。

• **支付状态机**：`not_required`（无偿无需支付）, `unpaid`（待支付）, `paid`（已支付）。

• **结算状态机**：`not_required`（无需结算）, `pending`（待结算）, `recorded`（已登记人工结算凭证）。
