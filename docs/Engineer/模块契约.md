## 2. 模块边界（集群与分支所有权）

每个集群拥有其前后端代码的完整修改权；跨集群只能调用 §3 冻结接口。分支策略经用户 2026-11 批准，**未经许可不许合并**。

| 集群 | 分支 | 后端包 | 前端目录 | 拥有的表 |
|---|---|---|---|---|
| 交易核心 | task | task、order、payment、review、complaint、category | task/、order/、review/ | tasks、orders、payment_attempts、settlement_records、reviews、complaints、categories |
| 消息集群 | chat | chat、notification | chat/、notification/ | conversations、conversation_members、messages、notifications |
| 账号集群 | user | user、verification、file、security、util | user/、views/（LoginRegister/Profile） | users、credit_events、credit_recovery_runs、verification_codes |
| 后台 | admin | admin | admin/ | 无自有表，**只读聚合 + 经域服务写入** |
| 数据库 | SQL | —（管 schema，不改业务代码） | — | 全部表结构，迁移脚本唯一入口 |
| 主干 | main | common、config（SecurityConfig 除外） | common/、router/、App.vue、main.js | — |

交易核心内部（task/order/payment/review/complaint）业务高度重合，允许实体级互引与同事务协作，不视为跨集群。

跨分支协调：SQL 分支的 schema 变更与功能分支的 JPA 实体变更必须同批评审、同时合并；新增端点需 user 分支同步 SecurityConfig 白名单。

## 3. 冻结接口

以下签名与语义已冻结。修改须走 §8 流程。

### 3.1 通知（消息集群 → 所有集群）

```java
// NotificationService，@Transactional
void createNotification(Long receiverId, String title, String content, String type)
```

- 调用方只传四个标量，**禁止传实体或要求回调**。
- 语义：同事务双写通知表 + 接收者的系统聊天会话（K2）。type 为业务事件标签（ORDER_ACCEPTED、PAYMENT、OVERDUE、CREDIT_CHANGE 等），新增 type 不需改签名。
- 只读查询：getUserNotifications / markAsRead / markAllAsRead / getUnreadCount，仅 receiverId 本人可操作。

### 3.2 信用分（账号集群 → 交易核心/后台）

```java
// CreditService，@Transactional
boolean adjust(Long userId, int delta, String eventKey, String reason)
```

- **唯一信用分写入口。** 任何域（含 admin）不得直接 setCreditScore（K1）。
- 幂等：eventKey 已存在且参数一致 → 返回 false 不重复扣分；参数不一致 → 409。
- 行锁保护，分数钳制 [0,100]。每次变更产生 CreditEvent 审计流水，支付撤销误罚依赖 `creditEvents.findByEventKey("overdue:"+orderId)` 对账。
- eventKey 命名约定：`overdue:{orderId}`、`overdue-reversal:{orderId}`、`review:{orderId}`、`admin:{orderId}:{operationId}`。

### 3.3 聊天联动（消息集群 → 交易核心/后台）

```java
// ChatIntegrationService，@Transactional（当前签名）
void createTeamGroup(Task task)
void handleAfterAccept(Task task, Long orderId, Long providerId)
void handleCancelOrder(Task task, Long userId, boolean isRequester)
void handleTaskCompleted(Task task)
```

- 业务域在生命周期节点调用，chat 负责建群/入群/私聊/解散提示。
- **待修（K3）**：参数收 Task 实体使 chat 耦合 task 字段。目标修订为标量参数（taskId、taskType、title、requesterId、maxMembers），修订须走 §8 流程，批准前维持现签名。
- 会话/消息 CRUD 仅 chat 域内与 admin 只读监管使用。

### 3.4 用户（账号集群 → 所有集群）

- `UserRepository` 只读方法（findById、findAll 等）与 `User` 实体字段冻结；`findLockedById` 为悲观写锁，跨域写用户状态必须经它。
- 用户状态/角色/信用分写入：仅 UserService 与 CreditService。admin 封禁、调分须调域服务（K1 待修）。
- `UserContext.getCurrentUserId()`：Controller 取当前身份的唯一方式，禁止接收客户端自报 userId/adminId。

### 3.5 统一响应（主干 → 所有集群）

```jsonc
// ApiResponse<T>，NON_NULL 序列化
{ "code": 200, "message": "success", "data": {}, "error": null }
// PageResult<T>，页码从 1 开始
{ "items": [], "pagination": { "page": 1, "pageSize": 20, "total": 0, "totalPages": 0 } }
```

- 业务错误抛 `BusinessException(code, message)`，由 GlobalExceptionHandler 统一转换；Controller 不得自拼错误 JSON。
- HTTP 200 携带 code≥400 视为失败（前端拦截器据此 reject）。

## 4. 依赖方向规则

**允许**：

- 交易核心内部任意互引（含同事务）。
- 任何域 → `NotificationService.createNotification`。
- 任何域 → user 只读 / `CreditService.adjust`。
- task/order/admin → `ChatIntegrationService`。
- chat → task 只读、user 只读（K3 修订后 chat 不再引 task 实体）。
- admin → 各域**只读 repository 聚合** + 各域 **service 写入**。

**禁止**：

- admin 直写其他域的 repository（K1，待修）。
- notification 依赖 chat 以外的任何域。
- chat 依赖 order/payment/review/complaint。
- 任何域绕过 CreditService 改信用分。
- 前端模块直调其他模块的私有组件（task 详情页嵌 OrderActions 为既有授权例外）；跨模块数据一律走对方 api.js 或 store。
- 新增跨集群依赖边：须先走 §8 契约修订。

## 5. 共享文件所有权

下列文件不归功能分支私有；修改须由所有权分支发起或经其确认，其他分支不得擅改。所有合并经用户批准。

| 所有权分支 | 文件 |
|---|---|
| main | `docs/`（含两份契约）、`common/*`、`config/BusinessTimeConfig`、`config/WebConfig`、`pom.xml`、前端 `router/index.js`、`App.vue`、`main.js`、`common/httpClient.js`、`common/http.js`、`vite.config.js`、`package.json` |
| SQL | `backend/SQL/*`、`application.yml` 数据库相关配置 |
| user | `config/SecurityConfig`（URL 授权白名单）、`security/*`、`util/*`、`user/User.java` 实体字段、`UserRepository` 接口签名、前端 `user/userStore.js` |

热点文件（router 路由表、SecurityConfig 白名单）的追加型改动：所有权分支小步提交，其他分支及时同步，避免语义冲突。新增端点的分支须提前向 user 分支申报白名单变更。

## 6. 前后端接缝契约

| 接缝 | 约定 |
|---|---|
| HTTP | 前端 baseURL `/v1`；Vite 代理重写为 `/api/v1` → 8080；生产部署须保证同路径映射 |
| 认证 | 请求头 `Authorization: Bearer <JWT>`；401 → 前端统一提示"请先登录" |
| WebSocket | `/api/ws/chat?token=<JWT>`（浏览器 WS 不能加 header）；消息类型 PING/PONG/SEND/MSG/RECALL；载荷 `{type, convId, message}`；仅 status=1 账号可连 |
| 上传 | `POST /v1/files/upload`（multipart）→ `data.url`；结算凭证走管理员鉴权接口，不公开映射 |
| 支付回调 | `POST /v1/payments/notify/{wechat,alipay}` 免认证，真实性由渠道 SDK 验签 |
| 时间 | 后端无时区 DATETIME 一律按 `+08:00` 解释（前端 orderPolicy.businessTime 已实现） |
| DTO 对齐 | 后端 DTO 字段增删改须同步前端 api/组件；无代码生成，**变更双方在同一 PR 或关联 PR 内完成** |
| 规则副本 | 前端 orderPolicy.js 是后端评价/付款规则的副本（K5）：后端规则变更必须同步修订 orderPolicy 及其单测 |
| 地址 | 禁止新增硬编码后端 origin（K6 现存 5 处待修）；文件 URL 统一走代理或配置注入 |

## 7. 数据库契约

- 迁移文件 `backend/SQL/` 主干专属，编号递增，只增不改历史文件。
- 外键拓扑：orders.task_id→tasks；orders.requester_id/provider_id→users；reviews.order_id→orders（unique）；payment_attempts.order_id→orders（order_id+active_slot 唯一）；settlement_records.order_id→orders；complaints.order_id→orders；messages.conv_id→conversations。
- **写权限**：每张表仅所有权集群（§2）可写。跨集群读允许。admin 现存的跨表直写为 K1 待修项。
- 订单状态机（OrderStatus/paymentStatus/settlementStatus/disputed）由交易核心独占解释；履约、支付、结算三态分离，completed 不代表已付款。
- 并发约定：订单写操作固定"任务→订单"锁顺序（OrderLocks）；信用分写操作先用户锁再查 eventKey。

## 8. 契约变更流程

1. 在讨论中拟定修订草案（改哪个接口、影响哪些集群、迁移方案）。
2. 用户/维护者明确批准。
3. 写入本文或 API 规范文档（外部 API 变更）。
4. 同步代码与测试；跨集群接口变更须通知所有受影响分支。
5. 提交遵循 CONTRIBUTING：Conventional Commits，单行，描述 ≤15 字符，一次一项。
