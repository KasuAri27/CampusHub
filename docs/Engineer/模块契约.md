> 本文定义模块边界、冻结接口与依赖规则，是多分支并行开发的协作依据。
> 契约神圣：未经用户/维护者批准，严禁修改本文与外部 API 契约（AGENTS §1）。
> 架构背景与已知问题编号（K1–K8）见 [架构文档](架构文档.md)。

## 2. 模块边界（集群与分支所有权）

每个集群拥有其后端代码的完整修改权；前端全部由 Frontend 分支维护（2026-11-19 起）。跨集群只能调用 §3 冻结接口。分支策略经用户 2026-11 批准，**未经许可不许合并**。

| 集群 | 分支 | 后端包 | 前端目录 | 拥有的表 |
|---|---|---|---|---|
| 交易核心 | task | task、order、payment、review、complaint、category | — | tasks、orders、payment_attempts、settlement_records、reviews、complaints、categories |
| 消息集群 | chat | chat、notification | — | conversations、conversation_members、messages、notifications |
| 账号集群 | user | user、verification、file、security、util | — | users、credit_events、credit_recovery_runs、verification_codes |
| 后台 | admin | admin | — | 无自有表，**只读聚合 + 经域服务写入** |
| 数据库全局件 | main | —（管建库/迁移登记/指纹/种子/断言） | — | 01 建库、migrations 登记、结构指纹、种子数据、ci-assertions |
| 主干 | main | common、config（SecurityConfig 除外） | — | — |
| 前端 | Frontend | — | `frontend/` 全部（task/、order/、review/、chat/、notification/、user/、views/、admin/、common/、router/、App.vue、main.js 及构建配置） | — |

交易核心内部（task/order/payment/review/complaint）业务高度重合，允许实体级互引与同事务协作，不视为跨集群。

前后端协作：后端分支改动接口或 DTO 前先按 §8 修订契约，改完后用会话消息通知 Frontend 对话；前端改动在 Frontend 分支完成，与后端改动作为关联 PR 一起合入 main（§6 DTO 对齐）。

跨分支协调：数据库结构变更与对应 JPA 实体变更必须同批评审、同时合并；域内建表脚本随表归所有权集群，全局件归 main；跨域结构改动走 AGENTS §6 通知协议；新增端点需 user 分支同步 SecurityConfig 白名单。

## 3. 冻结接口

以下签名与语义已冻结。修改须走 §8 流程。

### 3.1 通知（消息集群 → 所有集群）

```java
// NotificationService，@Transactional
void createNotification(Long receiverId, String title, String content, String type)
```

- 调用方只传四个标量，**禁止传实体或要求回调**。
- 语义：同事务双写通知表 + 接收者的系统聊天会话（K2）。type 为业务事件标签（ORDER_ACCEPTED、PAYMENT、OVERDUE、CREDIT_CHANGE 等），新增 type 不需改签名。
- 只读查询：getUserNotifications / markAsRead / markAllAsRead / getUnreadCount，仅 receiverId 本人可操作。

### 3.2 信用分（账号集群 → 交易核心/后台）

```java
// CreditService，@Transactional
boolean adjust(Long userId, int delta, String eventKey, String reason)
```

- **唯一信用分写入口。** 任何域（含 admin）不得直接 setCreditScore（K1 已修复）。
- 幂等：eventKey 已存在且参数一致 → 返回 false 不重复扣分；参数不一致 → 409。
- 行锁保护，分数钳制 [0,100]。每次变更产生 CreditEvent 审计流水，支付撤销误罚依赖 `creditEvents.findByEventKey("overdue:"+orderId)` 对账。
- eventKey 命名约定：`overdue:{orderId}`、`overdue-reversal:{orderId}`、`review:{orderId}`、`admin:{orderId}:{operationId}`（订单裁决类）、`admin:{targetUserId}:{operationId}`（后台手动调分，operationId 由客户端可选传入，缺省服务端生成 UUID，≤36 字符）。

### 3.3 聊天联动（消息集群 → 交易核心/后台）

```java
// ChatIntegrationService，@Transactional（2026-11-20 修订批准的目标签名）
void createTeamGroup(Long taskId, String title, Long requesterId, int maxMembers)
void handleAfterAccept(Long taskId, boolean team, String title, Long requesterId, Long orderId, Long providerId)
void handleCancelOrder(Long taskId, boolean team, Long userId, boolean isRequester)
```

- 业务域在生命周期节点调用，chat 负责建群/入群/私聊/解散提示。调用方只传标量；`team` 由调用方按需求类型（辨别列）判断，不得对懒加载代理使用 `instanceof`。
- 原 `handleTaskCompleted(Task)` 无调用方，修订后删除。
- **过渡期（K3，见 §9）**：代码现仍为收 `Task` 实体的旧签名，按 §9 所列步骤切换；切换完成前新旧签名可并存，新增调用一律使用标量版本。
- 会话/消息 CRUD 仅 chat 域内与 admin 只读监管使用。

### 3.4 用户（账号集群 → 所有集群）

- `UserRepository` 只读方法（findById、findAll 等）与 `User` 实体字段冻结；`findLockedById` 为悲观写锁，仅账号集群内部使用，其他域不得借它写用户。
- 2026-11-20 批准新增的只读方法（C7，取代全表加载后内存过滤）：

```java
// UserRepository
List<Long> findIdsByRole(User.Role role)   // 如通知全部管理员、全体广播只取 ID
long countByStatus(Integer status)         // 如仪表盘统计禁用账号数
```

- 用户状态/角色/信用分写入：仅 UserService 与 CreditService。调分调 `CreditService.adjust`（K1 已修复）。
- **封禁只能由管理员发起**，自动流程（定时任务、逾期扣分等）一律不得封禁：
  - 管理端账号开关：`UserService.toggleStatus(Long userId)`（调用方 admin 负责校验管理员身份）。
  - 管理员在业务处置中决定封禁（如逾期处置时勾选“同时禁用付款人账号”）：由所在域转调下列接口（2026-11-20 批准，K9）。

```java
// UserService，@Transactional（加入调用方事务）
boolean ban(Long userId, Long adminId)
```

  - 账号集群自行校验 `adminId` 为管理员，否则 403；目标为管理员账号时 400。
  - 幂等：取用户行锁后，已封禁返回 `false` 不重复写，否则置为封禁返回 `true`。
  - 不改信用分、不发通知（通知由调用方按业务发出）。用户锁为 §7 锁顺序的最后一层，调用方已持有的需求、订单锁不受影响。
- `UserContext.getCurrentUserId()`：Controller 取当前身份的唯一方式，禁止接收客户端自报 userId/adminId。

### 3.5 统一响应（主干 → 所有集群）

```jsonc
// ApiResponse<T>，NON_NULL 序列化
{ "code": 200, "message": "success", "data": {}, "error": null }
// PageResult<T>，页码从 1 开始
{ "items": [], "pagination": { "page": 1, "pageSize": 20, "total": 0, "totalPages": 0 } }
```

- 业务错误抛 `BusinessException(code, message)`，由 GlobalExceptionHandler 统一转换；Controller 不得自拼错误 JSON。
- HTTP 200 携带 code≥400 视为失败（前端拦截器据此 reject）。

### 3.6 需求只读视图（交易核心 → 消息集群，2026-11-20 批准，K3/K10）

```java
// TaskReadService（task 包），@Transactional(readOnly = true)
Optional<TaskChatView> findChatView(Long taskId)
Map<Long, TaskChatView> findChatViews(Collection<Long> taskIds)   // 批量，供会话列表与清理任务使用

record TaskChatView(
    Long taskId,
    boolean team,                 // 按辨别列判断
    String title,
    String status,                // Task.TaskStatus 名称
    Long requesterId,
    Integer maxMembers,           // 非组队为 null
    LocalDateTime deadline,
    LocalDateTime updatedAt,      // 群聊清理按此计算闲置时长
    boolean hasOpenObligations)   // 该需求存在订单处于争议中、待付款，或已付款但未登记结算
```

- chat 读取需求信息的唯一入口；chat 不得引用 `Task` 实体、`TaskRepository`、`OrderRepository`。
- `hasOpenObligations` 的判定与现行群聊清理条件一致，由交易核心负责解释订单状态机（§7），chat 不再自行判断付款与结算状态。

## 4. 依赖方向规则

**允许**：

- 交易核心内部任意互引（含同事务）。
- 任何域 → `NotificationService.createNotification`。
- 任何域 → user 只读 / `CreditService.adjust`。
- 交易核心 → `UserService.ban`（仅限管理员发起的处置，§3.4）。
- task/order → `ChatIntegrationService`（admin 经 `TaskService.approveByAdmin` 间接触发，不再直接依赖）。
- chat → `TaskReadService` 读取 `TaskChatView`（§3.6）、user 只读。chat 不引 task 实体与仓库（K3 过渡期见 §9）。
- admin → 各域**只读 repository 聚合** + 各域 **service 写入**。

**禁止**：

- admin 直写其他域的 repository（K1 已全部修复：分类增删改已改走 `CategoryService`，2026-11-26）。
- notification 依赖 chat 以外的任何域。
- chat 依赖 order/payment/review/complaint。
- 任何域绕过 CreditService 改信用分。
- 前端模块直调其他模块的私有组件（task 详情页嵌 OrderActions 为既有授权例外）；跨模块数据一律走对方 api.js 或 store。
- 新增跨集群依赖边：须先走 §8 契约修订。

## 6. 前后端接缝契约

| 接缝 | 约定 |
|---|---|
| HTTP | 前端 baseURL `/v1`；Vite 代理重写为 `/api/v1` → 8080；生产部署须保证同路径映射 |
| 认证 | 请求头 `Authorization: Bearer <JWT>`；401 → 前端统一提示"请先登录" |
| WebSocket | `/api/ws/chat?token=<JWT>`（浏览器 WS 不能加 header）；消息类型 PING/PONG/SEND/MSG/RECALL；载荷 `{type, convId, message}`；仅 status=1 账号可连 |
| 上传 | `POST /v1/files/upload`（multipart）→ `data.url`；结算凭证走管理员鉴权接口，不公开映射 |
| 支付回调 | `POST /v1/payments/notify/{wechat,alipay}` 免认证，真实性由渠道 SDK 验签 |
| 时间 | 后端无时区 DATETIME 一律按 `+08:00` 解释（前端 orderPolicy.businessTime 已实现） |
| DTO 对齐 | 后端 DTO 字段增删改须同步前端 api/组件；无代码生成。后端分支改完通知 Frontend 对话，**前后端改动作为关联 PR 一起合入 main** |
| 规则副本 | 前端 `order/orderPolicy.js`（评价窗口）与 `order/orderFlow.js`（验收、付款、逾期期限提示）是后端规则的副本（K5）：后端规则变更必须通知 Frontend 对话，同步修订这两个文件及其单测 |
| 地址 | 禁止新增硬编码后端 origin；文件 URL 统一走同源相对路径（K6 已修复） |

## 7. 数据库契约

- `backend/SQL/` 所有权按域下放（2026-11-14 用户批准取消 SQL 常设分支）：
  - **域内全量脚本**归对应集群：02 账号→user、03 交易核心→task、04 消息→chat；表结构变更直接修改对应脚本。
  - **全局件**归 main：01 建库、05 种子数据、`migrations/` 迁移登记、结构指纹与 `ci-assertions.env` 断言清单。
  - **升级脚本** `migrations/Mnnn-*.sql` 供旧库升级，编号递增、已发布只增不改；跨域迁移由 main 协调编号避免撞名。当前预留：**M006 归 task**，用于需求被驳回状态（`tasks.status` 增加 `rejected`，新增 `reject_reason VARCHAR(200)`、`rejected_at`，TODO §1.1）。
  - 每次结构变更须同时修改全量脚本并追加升级脚本；独立工作流 `sql-schema.yml` 比对“全新建库”与“旧库升级”两条路径的结构，必须一致。
- 外键拓扑：orders.task_id→tasks；orders.requester_id/provider_id→users；reviews.order_id→orders（unique）；payment_attempts.order_id→orders（order_id+active_slot 唯一）；settlement_records.order_id→orders；complaints.order_id→orders；messages.conv_id→conversations。
- **写权限**：每张表仅所有权集群（§2）可写。跨集群读允许。admin 的跨表直写（K1）已全部修复，分类增删改经交易核心的 `CategoryService`。
- 订单状态机（OrderStatus/paymentStatus/settlementStatus/disputed）由交易核心独占解释；履约、支付、结算三态分离，completed 不代表已付款。
- 并发约定：悲观写锁一律按 **需求 → 订单 → 支付单 → 用户** 的顺序获取，可以跳过前面的层级，但不能倒序。订单写操作经 `OrderLocks` 先锁需求再锁订单；支付、结算、评价只锁订单且不写需求行；信用分写操作先用户锁再查 eventKey。2026-11-20 审查：现有加锁路径均符合该顺序，未发现环路。

## 8. 契约变更流程

1. 在讨论中拟定修订草案（改哪个接口、影响哪些集群、迁移方案）。
2. 用户/维护者明确批准。
3. 写入本文或 API 规范文档（外部 API 变更）。
4. 同步代码与测试；跨集群接口变更须通知所有受影响分支。
5. 提交遵循 CONTRIBUTING：Conventional Commits，单行，描述 ≤15 字符，一次一项。
